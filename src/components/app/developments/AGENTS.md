- Developments use caller-RLS CRUD and transactional attachment, deletion and gallery RPCs; automatic ranges are read-time aggregates with separate manual overrides; Storia publishing uses the dedicated confirmed-parent developer-account queue. Why: preserve tenant isolation and existing property/portal lifecycles.
- Assigning existing listings to a development creates independent copies only through `clone_properties_to_development` (new id/reference, `cloned_from_property_id`, own photo files); originals are never modified. Copies with `development_id` use Storia only as developer-account units (selection intercepted in `applyPortalSelectionForOrg`, adapter never creates agency adverts); "remove from development" soft-deletes the copy. Why: the agency listing and its publications must stay untouched.
- Bulk allocation runs only as `development_clone_jobs`: `start_development_clone_job` checks rights/visibility as the caller and only enqueues; the worker (`/api/public/cron/development-clone`, kicked on enqueue plus a per-minute managed schedule) processes small batches via `development_clone_job_step`, which rechecks the requester's rights under their identity and keeps a pending item so resumed runs never duplicate copies; finish notifies via `notifications`. Why: large allocations must not time out in the request.
- Unit withdraw/republish/remove share that queue with caller-checked resumable steps; withdrawal intent blocks selections and automatic Storia preparation, and removal uses delete_property plus normal withdrawals. Why: copy-only background operations must not touch originals or silently republish withdrawn units.
- Parent portal choices live in development_portal_selections; the legacy trigger and service-only batch RPC enqueue one development_portal_jobs operation, with nullable changes falling back to legacy portal_key/enabled. A transaction-bound batch job covers its own selection writes; the worker groups enables/withdrawals by privilege within one unit step. Copies/republishing and feed/Partner parents read the same choices. Why: atomic multi-portal changes preserve existing jobs, tenant access and manual withdrawals.
- Development units take the development location only via DB trigger `properties_a_development_location` (column-list, sorts before `properties_public_slug`) and propagation `developments_location_propagate` → `align_development_units_location` (service_role only), when the development has county, city and map position; forms mirror it with `src/lib/developments/unit-location.ts`. Why: no write path (clone, form, import, AI) can diverge from the development location.

- Development outbound contacts and the informative publishing label share `src/lib/developments/contact.server.ts`; feed and Partner readers preload profiles in batches and pass resolved IDs to pure mappers. Why: one contact decision without changing assignment, access or unit contacts.
- Agent development rights live in `agent_development_permissions` (no row = none; admin/superadmin unrestricted): `developments_insert` checks `agent_can_create_development`, enabling portals is checked per actor in both selection server paths (`forbiddenDevelopmentPortal`) and by trigger `development_selection_permission_guard` on caller writes; disabling is always allowed. Why: restrictions follow the person making the change, not the development.
