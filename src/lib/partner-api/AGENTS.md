- Partner API reuses dynamic_feed_portals and typed portal_index_keys; index readers select key_type=index. Why: additive onboarding without changing legacy feeds or agency-owned portal_api_keys.
- Public handlers live under /api/public/partner/v1 and authenticate every operation; service-only atomic counters and receipts are durable, test agencies are explicitly allowlisted, and hourly SQL cleanup consolidates retention. Why: published-site bypass, no cross-environment data and no Worker-local state.
- Request journals contain only canonical route templates, method, status, prefix, portal, duration, request ID and a rate-check failure flag; never request payloads, queries, arbitrary path segments or credentials. Why: diagnostic privacy.- Read endpoints serve per-portal snapshots (partner_api_*_state + seq events) produced by sync.server.ts from the feed's selection/eligibility and mapPropertyToFeed; withdrawn listings are identity-only tombstones kept 30 days, and environment scoping is applied at read time. Why: one eligibility rule, stable incremental sync and no data from non-activated agencies.
- Sync runs via a database queue (row triggers on properties/images/publications/connections/profiles) drained every minute plus a full pass every 5 minutes, serialized by a lease row; each (portal, agency) applies in one RPC transaction. Why: saves stay fast and event order matches state.
- Partner POST feedback uses mandatory P1 receipts and service-only RPCs with current connection/environment checks; publication timestamps, message IDs, daily counters and email ten-minute claims are atomic. Dedicated feedback reads use property caller RLS and overlay existing portal cells/readiness; lead ingestion delegates to the unchanged ingestPortalLead contract. Why: preserve push semantics while isolating partner data and duplicate delivery.
- Partner webhooks run on Cloudflare Workers without accessible internal networking: HTTPS/443 hostname-only URLs, public-only DoH A+AAAA checks before saving and each delivery, and no redirects form the accepted protection for this deployment; DNS validation does not pin the subsequent fetch address. Why: the external Habitoo relay must not be changed, and this accepted runtime boundary avoids claiming general DNS-rebinding protection.
- Partner webhook configs and ordered outbox are scoped by portal/environment; encrypted secrets stay server-only, event inserts wake delivery, and retries reuse the existing Partner sync minute callback. Why: durable delivery without a new idle polling schedule, with isolated demo traffic.
