# Portal rules

- Imobiliare single-transaction replacement checks saved offer transactions, drafts and journals the old reference before publishing a deterministic transaction-suffixed reference; persistence excludes replaced offers. Why: retries reuse the same new reference without overwriting the opposite transaction.

- ClickImob, Imobli, Locuit and Imobiliare+ share a portal-parameterized index, signed-token resolver and feed-only adapter; each keeps its own secret, signing namespace, token prefix, publication filter and index-state key; Imobiliare+ stays off public pages until the portal confirms. Why: reuse identical grace/selection behavior without cross-portal access or changing ClickImob contracts.

- ZUP uses documented form OAuth, encrypted agency credentials, atomic state and refresh lock/CAS; login redirects/401 refresh once, 429 retries once and durable request reservations cap account traffic. Its atomic global catalogue feeds pure mapping and token-free SuperAdmin preview. Listing writes use the shared queue plus property lock and saved transaction IDs; pre-send creation fences reconcile only a unique recent title/price match, never auto-retry uncertain creates. Photos retain exact returned source→ID links, omit unchanged galleries and block unconfirmed deltas; status claims cap GETs to once/minute. Withdrawal always deactivates, never deletes; no type, featured or paid actions. Why: prevent duplicates, guessed links, secret leaks and undocumented gallery assumptions.

- Ofera mapping and location resolution are pure and consume only the active synchronized catalogue; a SuperAdmin-only read preview loads agency/assigned-agent/public-media data and platform currency without importing Ofera transport or token code. Preview itself never enables publishing. Why: unknown categories/options must be omitted or blocked, and inspecting a payload must not trigger external writes.

- Ofera partner authentication uses only global project secrets and a server-only encrypted text token, fenced database renewal lease and per-call redacted diagnostics; the body envelope is authoritative, with a validated plain OAuth token-response exception. Agency provider IDs use the SuperAdmin connection flow. Why: concurrent Workers must share one partner token without leaking credentials.
- Ofera push operations reuse the existing queue with a scoped durable ofera_intent for activation-only/confirmed resend; per-transaction states fence non-idempotent creates before sending, omit unchanged image galleries, and save before activation. Soft deletion deactivates; hard/account deletion supplies DELETE intent before removing the property. No expiry job or automatic create-timeout retry. Why: avoid duplicates, lost created IDs and deletion on reversible soft-delete.
- Ofera nomenclature uses unauthenticated GETs, strict whole-download validation and one advisory-locked transactional apply RPC; unchanged rows retain timestamps, missing IDs deactivate, detailed real-estate parameters drive atomic SuperAdmin alerts, and cities retain only count/hash in audit. Weekly managed callbacks skip unless an agency has activated Ofera. Zones preserve original parent IDs even when absent from the public cities list. Why: retain source fidelity, prevent partial catalogues and avoid invented geography or publishing behavior.

- Storia renewal overrides are resolved in the pure mapper; renewal saves reuse the atomic content-update queue with pending eligibility, worker checks, and per-advert remote revalidation. Update mode never creates or activates adverts; agency expiry republication remains separate. Why: renewal choices must not reactivate inactive adverts or lose changes on busy jobs.

- Contact refresh after reassignment uses `portal_publish_jobs.operation=update`, only already-active pairs, with worker state revalidation and journal `update`; pending contact requests on busy jobs drain transactionally through queue claim. Why: no new publication, withdrawal, promotion or lost contact update during concurrent publishing.

- Pre-publish requirements live only in `src/lib/portals/requirements.ts` (`PORTAL_REQUIREMENTS` + `validatePortalRequirements`), loaded by `requirements.server.ts` (single + batch); `executeListingAction` blocks publish/update/republish with VALIDATION_ERROR before any portal call, withdraw is never blocked; the Publicare tab and the bulk grid disable enabling a portal with missing fields. Why: one rule set for UI, grid and server; published listings are never auto-withdrawn over a newly required field.
- Portal logo summaries link to the listing only through `portalListingLink` in `src/lib/portals/listing-links.ts`: https `portal_listings.public_url` saved from the portal's real response, only for published/in_feed; never construct or guess URLs (ClickImob's `/anunt/<slug>-<id>` soft-404s on id alone). Why: no invented links.
- Imobiliare.ro floor preflight shares the mapper's pure validation and runs before authorization, catalog refresh or agent sync; seller commission is parsed only in its mapper. Why: invalid apartments must not call the portal and other integrations remain unchanged.

- Properstar index tracks agency presence with 7-day deletion grace; links use HMAC-SHA256. Why: one index URL; deactivation has no timestamp elsewhere.
- ClickImob index: JSON index at /api/public/feed/clickimob/index/{CLICKIMOB_INDEX_KEY}.json reuses Properstar index rules; state in `portal_index_state` (portal column), agencies with per-agency ClickImob connection excluded. Why: no duplicate listings.
- Bulk portal changes use durable `portal_bulk_jobs`/`portal_bulk_items`, processed by an armed cron through `applyPortalSelectionForOrg`; UI requests never call adapters directly. Why: jobs survive navigation and keep portal rules, retries and audit.
- Portal connection status shown in the UI has exactly three values (connected/error/disconnected), computed only by `portalDisplayStatus` in `src/lib/portals/registry.ts`; raw DB values never reach the UI. Why: one rule.
- Facebook Catalog card state (connected/error/disconnected) is computed only by `facebookCatalogState` in `src/lib/facebook-catalog-status.ts`; card counts reuse `loadFacebookCatalogInput` + `buildFacebookCatalogCsv`. Why: one rule for the feed and the card, no token ever returned.
- Self-service portal activation uses `selfActivatePortalForSession` (mode from `PortalDefinition.activation`); new orgs get ClickImob via trigger `t_org_auto_clickimob`. Why: one path for every org creation.
- Facebook Catalog token is a `site_feed_tokens` row `scope = facebook_catalog` (encrypted), accepted only with `allowFacebookCatalogToken`. Why: no site-token exposure.
- Facebook Catalog opt-ins use `portal_publications` key `facebook_catalog` without slots. Admins always manage them; agents manage only owned listings when the organization setting allows it. Why: feed inclusion requires an authorized explicit choice.
- Promotion catalogs are registered separately from listing portals and are merged only into the agency Settings portal list. Why: Catalog Facebook must look like a portal without entering portal publication, slot, activation, or withdrawal flows.
- Table `agent_portal_preferences` is kept but unused by code: Publicare never preselects portals. Why: "Portalurile mele" was removed; data preserved.
- Property publication cards share checkbox state and query only the assigned agent's slots; the server checks publication. Why: no duplicate state.
- Public portal grids share registry data. Why: sync.
- The integrations overview derives groups, badges and lead claims from registry metadata in a separate presentation module. Why: no duplicates or false claims; detail pages and publishing stay unchanged.
- Failure alerts use stable IDs per org, listing, portal, error and user. Why: no duplicates.
- Storia webhook requires the documented OLX signature (401 otherwise), processes inline within 1500 ms (`processWithinBudget`) then returns 200; timeouts/failures arm the retry cron (`storia_webhook_retry_arm`, max 5 attempts) because post-response work does not run in production; `portal_listings.last_event_at` drops older events. Why: OLX wants <2s replies and gives no ordering.
- Storia messages with no recognised listing go only to `portal_unmatched_messages` (SuperAdmin-only, manual assignment); never guess an agency. Leads group by `conversation_id`; every message notifies the agent. Why: no cross-agency leaks, no lost messages.
- Property-page portal publish/update/withdraw is a durable server queue: `enqueuePortalPublishJobs` inserts one `portal_publish_jobs` row per portal (one active per property+portal) and returns; `/api/public/cron/portal-publish` (nonce/cron secret, woken on enqueue + cron armed only while jobs are active) claims with SKIP LOCKED, max 3 parallel, ~25 s, 5-min lease, 3 transient retries, and runs `applyPortalSelectionForOrg` for that single portal as the requester. Why: publishing must not depend on an open page.
- VDI.ro: the listing agent is ensured on the current account (`/api` add/edit, account-scoped mapping in `portal_agent_links`, immutable numeric `external_id`) before every listing; unchanged same-account agents are not resent; listing `idintern` is the numeric part of the property reference, stored as `portal_listings.external_id` and never recomputed; `optiuni` is never sent until a confirmed value list exists. Why: VDI rejects listings with unknown agents or unknown amenities and matches updates by idintern.
- Portals whose API key is issued by the portal after a Habitoo request (Imospot, VDI.ro) are listed in `KEY_REQUEST_PORTALS` (`imospot-key-request.ts`): `activation: "approval"`, auto-approved request, one email per request (`provider_notified_at`), per-portal recipient/cc/sender/text in `platform_settings`; the key is entered only by SuperAdmin. Why: one flow, no duplicated code; a portal without a key is never "Conectat".
- VDI.ro leads: webhook `/api/public/portal/v1/vdi/leads` picks the agency by `agentie_id` = `portal_connections.external_account_id`, verifies `X-VDI-Semnatura` (HMAC-SHA256 of the raw body, per-agency secret in `settings.webhook_secret_encrypted`, constant time; 401 otherwise), saves to `portal_webhook_events` with `external_event_id = lead.id` (unique, dedupe) before 2xx, processes inline ≤1500 ms; cron `vdi_leads_arm`/`vdi-leads` retries and polls `GET /apileaduri` (cursor in `settings.leads_cursor`) only while a VDI connection has a key. Unknown listing → `portal_unmatched_messages`. All VDI API calls go through a 30/min per-key limiter; 429 is a retry. Why: same guarantees as Storia; no cross-agency leaks.
- OLX.ro direct (`olx_direct`, OAuth Partner API 2.0, `src/lib/portals/olx/`) uses its own secrets `OLXRO_CLIENT_ID`/`OLXRO_CLIENT_SECRET`, never the Storia `OLX_*` secrets; it can be active and connected alongside `storia`. Publishing (`adapters/olx-direct.server.ts`): POST /adverts, PUT full payload, withdraw = `deactivate` (is_success:false), republish = activate + PUT, DELETE only for deleted properties; "Publicat" only when `GET /adverts/{id}` says `active` (cron `olx_direct_status_arm`/`olx-status` while listings are pending); `limited`/`unpaid` activate only from an existing packet with `left > 0`. Taxonomy cached in `portal_taxonomy_cache` (`olx_direct`, weekly TTL, client_credentials GET only). Rotated refresh tokens are always saved; daily cron `olx_direct_refresh_arm`/`olx-token-refresh`; `invalid_grant` → reconnect + one admin notification. Why: separate OLX app and credentials.
- Habitoo never buys OLX packets or promotions: `olxPartnerRequest` blocks every POST to `/packets`, `/users/me/packets`, `/adverts/{id}/packets` and `/paid-features` (`isForbiddenOlxPurchase`). Why: spending is the agency's decision on OLX.
- OLX direct failures go through `olxFail` (`adapters/olx-direct.server.ts`): message = "<Portal> – <step>: <exact OLX HTTP text or real exception>", `detail` = technical code logged as `error_code`, HTTP status/body kept for `portal_response`; never the generic portal text. OLX calls in workerd must wrap `fetch` (unbound `fetch` → "Illegal invocation"). Why: errors must be diagnosable.
- OLX direct never creates duplicates: before every `POST /adverts` and after a POST timeout/5xx, look up `GET /adverts?external_id=<HB ref>` (strict match, ignore `removed_by_user`) and reuse that id. `limited`/`unpaid` without a packet is status `needs_packet` (not an error, one notification); the status cron runs every 3 min while listings are `pending` and hourly while only `needs_packet` remain, activating from an existing packet. Why: OLX may create the advert even when the reply times out; a missing packet is the agency's decision.
- Properstar leads resolve `agent_id` among the agency's members via `properstarEntityId("ag", userId)` and assign to that agent before the listing's agent; `listing_id` starting with `ag` (or equal to `agent_id`) is a direct agent-page message: no property lookup, 404 `agent_not_found` if unknown. Why: matches the AgentId Properstar reads from our feed.
- Storia `/meta` sync is a read-only fallback for notifications: `/api/public/cron/storia-meta` (nonce `storia_meta`) runs `mode=pending` every 5 min (only while Storia listings are pending ≤48h) and `mode=reconcile` every 6 h (paged `GET /advert/v1/meta`), max 2 req/s per agency; rows become synthetic notifications applied through `processLifecycle`, skipped when older than `last_event_at` or unchanged (`metaSyncDecision`). Why: OLX may not send notifications; notifications stay authoritative.
- Storia VAS (`vas_lifecycle`/`publish_vas`) is handled only in `vas.server.ts`: listing found by `data.advert_uuid`, never `object_id`; only `promotion_code=olx` has an effect, storing the OLX link per transaction in `portal_listings.portal_offers` (label `OLX`, reference `OLX:<tx>`), shown via `visibleOlxLinks` only while the Storia listing is published; other promotions are marked processed without effect. Recovery reads `GET /vas/v1/advert/{uuid}` in the 6-hour reconcile (403 = no `read:vas`, skipped). Why: Habitoo never buys or applies promotions, it only mirrors the export link.
- Outbound calls to portals that only accept approved IPs (VDI.ro, Imobiliare.ro) go through the fixed-IP relay whose public address `https://relay.habitoo.ro` is the code default (`RELAY_DEFAULT_URL`, overridable by the `PORTAL_RELAY_URL` secret); the relay is used only when `PORTAL_RELAY_KEY` is set, every relayed request carries `X-Relay-Key`, and the key never appears in logs or error messages. Why: Cloudflare egress IPs vary, the relay address is public but the key must stay secret.
- Scheduled per-portal publishing lives in `portal_publish_schedules`; the per-minute `/api/public/cron/portal-schedules` checks for due rows first and only enqueues through `enqueuePublishJobsForOrg` (`fromSchedule`), which also cancels active schedules on manual publish/deselect. Why: one publishing path, same checks as manual.
- Bulk republish of already-published listings runs as `portal_publish_jobs` with `operation=republish` grouped by `portal_republish_batches` (one running per agency); the worker only calls `executeListingAction` update with label `republish`. Why: reuse the durable queue/retries and never publish, withdraw or promote.
- Regular republish completion notifications are created atomically by the batch status trigger, keyed by batch ID and linked to the property-list report parameter; the UI closes after durable enqueue and tracks user/agency-scoped batch IDs. Imoradar completion stays separate. Why: reports survive closed pages and retries cannot lose or duplicate notifications.
- Key-request emails (Imospot, VDI.ro) use `notifyKeyRequest` over `KEY_REQUEST_PORTALS`; `provider_notified_at` prevents duplicates. Why: one send, one flow for every portal.
- VDI agent synchronization is account-scoped in `portal_agent_links.external_account_id`; connection-account changes reset sync through a database trigger, and listing missing-agent recovery is limited to one add and one retry. Why: immutable agent IDs can exist on the old account but not the current one.
- Imobiliare.ro card mode travels in `portal_publish_jobs.imobiliare_mode`, requested publication mode and confirmed listing mode stay separate; status switches share one promotions POST inside the existing listing lock and withdrawal drafts both destinations. Bonus bypasses allocation/inventory checks and imoradar-only sends no promotions or slot reads; other services retain validation and per-service confirmation. Why: API section 18 separates destinations and lets the portal decide publication capacity.
- Imobiliare.ro promotion writes treat any `promotion_warnings` entry as failure (portal text shown, logged success=false); warning-free writes upsert `imobiliare_promotion_states` (org RLS, service_role writes), and card state merges portal listing body > slot-list membership > local state, with stop always allowed when unknown. Why: the POST response `data` has no `promotions` key, so local state is the only confirmation, and a warning means the service was not applied.
- `promote_imoradar` is the only exception: the account-inactive imoradar warning counts as applied (logged only); rules live in `imobiliare/imoradar-auto.ts`. Auto-send happens only after a successful Imobiliare.ro `publish`, honoring the agency setting (`portal_connections.settings.auto_imoradar`, default on), per-listing `portal_publications.imoradar_opt_out` and `imobiliare_promotion_states.manually_stopped` (any written `false`); the bulk action reuses `portal_publish_jobs` (operation `imoradar`) and `portal_republish_batches` (kind `imoradar`). Why: listings reach imoradar24 only with this flag, and manual stops must stick.
- Timeout/network failures (`TIMEOUT`, `NETWORK_ERROR`, "în timp util") follow only `src/lib/portals/transient-failure.ts`: automatic retries (30 s, 2 min) only for `TIMEOUT_RETRY_PORTALS` in the publish queue and bulk queue; an already-published listing whose update times out keeps its status with `UNCONFIRMED_UPDATE_NOTE` and a Retrimite button, never "Eroare"; `logOperation` receives `durationMs` for every operation that calls a portal. Why: retrying non-idempotent portals could duplicate listings, and an unconfirmed update is not a rejection.
- Republish/imoradar batches start only through RPC `start_portal_republish_batch` (batch, set-based job insert with ON CONFLICT skip, audit and `portal_publish_arm` in one transaction); `close_stale_republish_batches` (run before every active-batch check) closes running batches idle >15 min. Why: an interrupted request must never leave half a batch or block new republishes.
- Every portal queue start (republish, status withdrawals, contact updates, bulk publishing, property-page publishing) is one SECURITY DEFINER `start_*` RPC that writes all rows and arms its worker in one transaction, and first runs that queue's `close_stale_*` (>15 min without active jobs). Why: an interrupted request must never leave half-queued work.
- imo24.ro (`src/lib/portals/imo24/`): HTTPS-only client to https://imo24.ro/api/v1 with `redirect: "manual"`, key format checked by `imo24/key.ts` (also via registry `validate: "imo24_key"`), 401 never retried and the key cooled down 15 min, retries only on 429/5xx/network, local slowdown from `X-RateLimit-*`; `/credite` is refused in code. Stays off the public homepage list until it is verified live. Why: HTTP redirects turn POST into GET, 60 401s/hour block the IP, and no false integration claims.
- imo24.ro body mapping lives only in `imo24/mapper.ts` (pure; BNR rate and `/enumerari`/`/dotari` dictionaries passed in, dictionaries cached 24 h in `imo24/dictionaries.ts`); its blocking reasons reach the Publicare card via `PortalRequirementSpec.mapperReasons`. Why: one rule set for preview and publishing, no guessed enum values.
- imo24.ro publishing (`adapters/imo24.server.ts` + pure `imo24/publish.ts`): one `PUT /anunturi/by-external/{ref}-v|-i` per transaction, `portal_listings.external_id` = comma-joined codes, stale codes DELETEd; `camp_imutabil` → DELETE same code then PUT; `imagini_amanate` re-PUT via RPC `schedule_imo24_image_retry` (counter table `imo24_image_retries`, max 3, +10 min, busy jobs keep the delay through `portal_publish_jobs.followup_at`); agent email only when active in cached `GET /agenti` (1 h); success messages are logged for the card. Why: the portal keys listings by our code and downloads images asynchronously.
- Imopedia.ro uses hand-built SOAP 1.1 RPC/encoded envelopes and a minimal parser in `imopedia/soap.ts` (client in `soap.server.ts`); test connection is login → viewAgency → logout in finally and logs redacted raw XML (≤20 KB). Portals without `publish_listing`/`feed_pull` are hidden from the property Publicare list. Why: no native SOAP on Workers and the response shape is unpublished.
- Imopedia location: nomenclature lives only in `imopedia_regions`/`imopedia_areas` (SuperAdmin import in `imopedia/nomenclature.functions.ts`, validation and idempotent plan in `nomenclature.ts`; missing nodes become `usable_in_api=false`, never deleted); `REGION_ID`/`ZONA_ID` come only from pure `resolveImopediaLocation` (`imopedia/location.ts`), which checks the branch and leaves ZONA_ID empty on zero or ambiguous matches. Why: names repeat within a region and the tree is separate from Imobiliare.ro.
- Imopedia offer mapping lives only in pure `imopedia/mapper.ts` (`mapPropertyToImopedia`); every sent field must be typed in `IMOPEDIA_FIELD_TYPES` and legacy fields are dropped; feature lists match only the static nomenclature JSON in `imopedia/nomenclatures/` per TIP_IMOBIL_REAL; preview (`preview.functions.ts`) is SuperAdmin read-only with no portal call. Why: Imopedia's SOAP typing is strict and editorial rules forbid contact data.
- Imopedia publishing (`adapters/imopedia.server.ts`, pure rules in `imopedia/publish.ts`): one SOAP session per job (login → saveAgent only when the contact fingerprint changed → saveProperty → logout in finally; one re-login + one retry on "Invalid or expired session."); `ID_LOCAL` = digits of the property reference, stored as `portal_listings.external_id` and never recomputed; `AGENT_ID` = `portal_agent_links.external_id` (portal `imopedia`, account = AGENTIA); a different returned ID_LOCAL is an error; withdraw = deleteProperty and is idempotent; blocking reasons reach Publicare through `imopediaBlockingReasons`. Exception to "no constructed URLs": `public_url` = `https://www.imopedia.ro/anunt/proprietate-{AGENTIA}RUN{ID_LOCAL}`, the formula documented by Imopedia (docs.imopedia.ro/concepts). Why: fixed ID_LOCAL makes timeout retries safe and Imopedia shows the agent as contact.
- Imopedia media (`imopedia/media.ts`, `syncImopediaMedia`) runs only after a valid saveProperty in the same session: FILE_URL from the Habitoo media proxy, `FILE_ID = hb-<image id>-<8 hex of file identity hash>`, existsFile/addFile for files missing from `imopedia_listing_files`, syncFiles never with an empty list (deleteFile per file when none remain); media failures are warnings and never fail the listing. Why: Imopedia downloads by URL, has no documented reorder, and a saved offer must stay published.
- Imopedia Gold = the generic "Promovat" flag (`GOLD` 1/0 sent on every save); a Gold refusal saves Standard and returns `promotedConfirmed: false`, which unchecks the flag. Boost (`imopedia/boost.functions.ts`) uses saveBoost with offerId = ID_LOCAL, availability from viewAgency cached 5 min, no retry, logged as operation `boost`. Why: Gold limits are the agency's package; boosts are consumable.
- ZonaTa.ro (`src/lib/portals/zonata/`): HTTPS-only client to https://zonata.ro/api/v1 (Bearer `zt_live_`/`zt_test_`, validated by `zonata/key.ts`), method-specific deadlines including response body, per-key sliding-window limiter below 300/10 min and one paused retry on 429; only key mode is stored in settings. POST timeout recovery reads the exact external_id only for live keys. Images are signed in one property-media batch; preview replaces capabilities with paths. Queue attempts write a pending journal before preflight, finalize on return/throw, and mark abandoned attempts interrupted on reclaim. Why: avoid slow media redirects, duplicate writes, exposed tokens and missing evidence after termination; other portals keep their existing paths.
- ZonaTa nomenclature lives in `zonata_subcategories` (global, superadmin-read RLS, service_role writes; fields as jsonb) with each sync's raw `/categories` and diff in `zonata_nomenclature_syncs`; sync uses a saved agency key, GET only. Body mapping is pure in `zonata/mapper.ts` (fields only to nomenclature slugs/options) and its reasons reach Publicare via `zonataReasons`. Why: undocumented response shapes must stay inspectable and unknown values are never guessed.
- ZonaTa: per-transaction state (test/in_review/active/rejected/withdrawn/sold/expired) lives in `zonata_listings`; `portal_listings.status` holds only the mapped coarse status. Test keys never set external_id or published state. Why: the DB status vocabulary is fixed and test-mode must not consume slots.
- HomeDirect.ro (`src/lib/portals/homedirect/`): locations resolve county → city → district via HomeDirect `/locations/*` with a 30-day `homedirect_location_cache` (authenticated read, service_role write; no key → "unverified", which blocks only publishing); body mapping is pure in `homedirect/mapper.ts` and sends IDs, never `address`. Why: one lookup per location and HomeDirect owns its location vocabulary.
- HomeDirect publishing: per-transaction state (HomeDirect id/shortId/slug/status) lives in `homedirect_listings`; public URL only from the real `slug`. Withdraw = PATCH status (inactive / sold / rented by property status); DELETE only for soft-deleted properties. Agency fingerprint in `portal_connections.settings.agency_fingerprint`, agent fingerprint in `portal_agent_links`; PUT /agencies|/agents only when a previously sent fingerprint changes. Why: idempotent on externalIds.post and no needless account updates.
- Agency admins configure/test/activate portals only via `src/lib/agency-portal-setup.functions.ts` (org from session, secrets write-only, 10 s test limit, audit source `agency`), which reuses the SuperAdmin cores in `portals.functions.ts`. Why: one logic for both roles without exposing credentials.
- Vumsi (Orion) uses one global partner key (`VUMSI_API_KEY`, header X-Api-Key) in a GET-only server client capped at 2 req/s, one 429 retry and no 401/403 retry; nomenclature syncs store whole read-only snapshots in `vumsi_nomenclature_snapshots` and publishing stays `publish_coming_soon` until stage 3. Category/type correspondences, city cache and found account UUIDs live in `vumsi_*` tables; the pure mapper reads IDs only from the snapshot and those correspondences, and the SuperAdmin preview performs only GET lookups. Why: no hardcoded Vumsi IDs and no writes before the mapping is confirmed.
