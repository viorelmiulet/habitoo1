# Portal rules

- Properstar index tracks agency presence with 7-day deletion grace; links use HMAC-SHA256. Why: one index URL; deactivation has no timestamp elsewhere.
- ClickImob index: JSON index at /api/public/feed/clickimob/index/{CLICKIMOB_INDEX_KEY}.json reuses Properstar index rules; state in `portal_index_state` (portal column), agencies with per-agency ClickImob connection excluded. Why: no duplicate listings.
- Bulk portal changes use durable `portal_bulk_jobs`/`portal_bulk_items`, processed by an armed cron through `applyPortalSelectionForOrg`; UI requests never call adapters directly. Why: jobs survive navigation and keep portal rules, retries and audit.
- Portal connection status shown in the UI has exactly three values (connected/error/disconnected), computed only by `portalDisplayStatus` in `src/lib/portals/registry.ts`; raw DB values never reach the UI. Why: one rule.
- Facebook Catalog card state (connected/error/disconnected) is computed only by `facebookCatalogState` in `src/lib/facebook-catalog-status.ts`; card counts reuse `loadFacebookCatalogInput` + `buildFacebookCatalogCsv`. Why: one rule for the feed and the card, no token ever returned.
- Self-service portal activation uses `selfActivatePortalForSession` (mode from `PortalDefinition.activation`); new orgs get ClickImob via trigger `t_org_auto_clickimob`. Why: one path for every org creation.
- Facebook Catalog token is a `site_feed_tokens` row `scope = facebook_catalog` (encrypted), accepted only with `allowFacebookCatalogToken`. Why: no site-token exposure.
- Facebook Catalog opt-ins use `portal_publications` key `facebook_catalog` without slots. Admins always manage them; agents manage only owned listings when the organization setting allows it. Why: feed inclusion requires an authorized explicit choice.
- Promotion catalogs are registered separately from listing portals and are merged only into the agency Settings portal list. Why: Catalog Facebook must look like a portal without entering portal publication, slot, activation, or withdrawal flows.
- Table `agent_portal_preferences` is kept but unused by code: Publicare never preselects portals. Why: "Portalurile mele" was removed; data preserved.
- Property publication cards share checkbox state and query only the assigned agent's slots; the server checks publication. Why: no duplicate state.
- Public portal grids share registry data. Why: sync.
- Failure alerts use stable IDs per org, listing, portal, error and user. Why: no duplicates.
- Storia webhook requires the documented OLX signature (401 otherwise), processes inline within 1500 ms (`processWithinBudget`) then returns 200; timeouts/failures arm the retry cron (`storia_webhook_retry_arm`, max 5 attempts) because post-response work does not run in production; `portal_listings.last_event_at` drops older events. Why: OLX wants <2s replies and gives no ordering.
- Storia messages with no recognised listing go only to `portal_unmatched_messages` (SuperAdmin-only, manual assignment); never guess an agency. Leads group by `conversation_id`; every message notifies the agent. Why: no cross-agency leaks, no lost messages.
- Property-page portal publish/update/withdraw is a durable server queue: `enqueuePortalPublishJobs` inserts one `portal_publish_jobs` row per portal (one active per property+portal) and returns; `/api/public/cron/portal-publish` (nonce/cron secret, woken on enqueue + cron armed only while jobs are active) claims with SKIP LOCKED, max 3 parallel, ~25 s, 5-min lease, 3 transient retries, and runs `applyPortalSelectionForOrg` for that single portal as the requester. Why: publishing must not depend on an open page.
- VDI.ro: the listing agent is sent (`/api` add/mod, mapping in `portal_agent_links`, immutable numeric `external_id`) before every listing; listing `idintern` is the numeric part of the property reference, stored as `portal_listings.external_id` and never recomputed; `optiuni` is never sent until a confirmed value list exists. Why: VDI rejects listings with unknown agents or unknown amenities and matches updates by idintern.
- Portals whose API key is issued by the portal after a Habitoo request (Imospot, VDI.ro) are listed in `KEY_REQUEST_PORTALS` (`imospot-key-request.ts`): `activation: "approval"`, auto-approved request, one email per request (`provider_notified_at`), per-portal recipient/cc/sender/text in `platform_settings`; the key is entered only by SuperAdmin. Why: one flow, no duplicated code; a portal without a key is never "Conectat".
- VDI.ro leads: webhook `/api/public/portal/v1/vdi/leads` picks the agency by `agentie_id` = `portal_connections.external_account_id`, verifies `X-VDI-Semnatura` (HMAC-SHA256 of the raw body, per-agency secret in `settings.webhook_secret_encrypted`, constant time; 401 otherwise), saves to `portal_webhook_events` with `external_event_id = lead.id` (unique, dedupe) before 2xx, processes inline ≤1500 ms; cron `vdi_leads_arm`/`vdi-leads` retries and polls `GET /apileaduri` (cursor in `settings.leads_cursor`) only while a VDI connection has a key. Unknown listing → `portal_unmatched_messages`. All VDI API calls go through a 30/min per-key limiter; 429 is a retry. Why: same guarantees as Storia; no cross-agency leaks.
- OLX.ro direct (`olx_direct`, OAuth Partner API 2.0, `src/lib/portals/olx/`) uses its own secrets `OLXRO_CLIENT_ID`/`OLXRO_CLIENT_SECRET`, never the Storia `OLX_*` secrets; it can be active and connected alongside `storia`. Publishing (`adapters/olx-direct.server.ts`): POST /adverts, PUT full payload, withdraw = `deactivate` (is_success:false), republish = activate + PUT, DELETE only for deleted properties; "Publicat" only when `GET /adverts/{id}` says `active` (cron `olx_direct_status_arm`/`olx-status` while listings are pending); `limited`/`unpaid` activate only from an existing packet with `left > 0`. Taxonomy cached in `portal_taxonomy_cache` (`olx_direct`, weekly TTL, client_credentials GET only). Rotated refresh tokens are always saved; daily cron `olx_direct_refresh_arm`/`olx-token-refresh`; `invalid_grant` → reconnect + one admin notification. Why: separate OLX app and credentials.
- Habitoo never buys OLX packets or promotions: `olxPartnerRequest` blocks every POST to `/packets`, `/users/me/packets`, `/adverts/{id}/packets` and `/paid-features` (`isForbiddenOlxPurchase`). Why: spending is the agency's decision on OLX.
- OLX direct failures go through `olxFail` (`adapters/olx-direct.server.ts`): message = "<Portal> – <step>: <exact OLX HTTP text or real exception>", `detail` = technical code logged as `error_code`, HTTP status/body kept for `portal_response`; never the generic portal text. OLX calls in workerd must wrap `fetch` (unbound `fetch` → "Illegal invocation"). Why: errors must be diagnosable.
- OLX direct never creates duplicates: before every `POST /adverts` and after a POST timeout/5xx, look up `GET /adverts?external_id=<HB ref>` (strict match, ignore `removed_by_user`) and reuse that id. `limited`/`unpaid` without a packet is status `needs_packet` (not an error, one notification); the status cron runs every 3 min while listings are `pending` and hourly while only `needs_packet` remain, activating from an existing packet. Why: OLX may create the advert even when the reply times out; a missing packet is the agency's decision.
